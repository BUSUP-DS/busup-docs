# Text input

Inputs allow users to enter and edit text in interfaces. They are essential for forms, search fields, and data entry within the BUSUP ecosystem.

## Component States

### Default
The resting state before the user interacts. Placeholder text is shown in `Neutral 100` (`#dbdbdb`).

<TextInput
  label="Full Name"
  placeholder="e.g. John Doe"
  hint="Enter your name as it appears on your ID."
/>

### Active (Focus)
Triggered when the user clicks or tabs into the field. The border changes to `Neutral 300` (`#989898`) and the placeholder becomes typed text in `Neutral 400` (`#414141`).

<TextInput
  label="Full Name"
  placeholder="John Doe"
  hint="Enter your name as it appears on your ID."
/>

### With Slot Content
Inputs support independent left and right slots for additional context or actions.

<TextInput
  label="Search Route"
  placeholder="Enter city or code..."
  icon="🔍"
  hint="Try searching by the route number."
/>

### Error
Triggered when validation fails or a required field is submitted empty. Border and hint text switch to `Danger 300` (`#e53935`).

<TextInput
  label="Email Address"
  placeholder="user@domain"
  state="error"
  hint="Please enter a valid email address."
  required={true}
/>

### Disabled
Used when a field is locked and cannot be edited. Background becomes `Neutral 100` (`#dbdbdb`), label and hint render in `Neutral 200` (`#c4c4c4`).

<TextInput
  label="Route ID"
  placeholder="RT-192"
  state="disabled"
  hint="This field is automatically generated by the system."
/>

## Component API

| Property | Type | Default | Description |
|:---|:---|:---|:---|
| `label` | `string` | — | Text displayed above the input field. |
| `placeholder` | `string` | — | Hint text shown inside the field before the user types. |
| `hint` | `string?` | — | Supplementary text below the field — context or error feedback. |
| `state` | `'default' \| 'error' \| 'disabled'` | `'default'` | Controls visual state and interaction behavior. |
| `required` | `boolean` | `false` | If `true`, shows a red asterisk (`*`) next to the label. |
| `leftSlot` | `node` | — | Optional element in the left slot — icon, flag, chip, or any 16px element. |
| `rightSlot` | `node` | — | Optional element in the right slot — icon, clear button, or any 16px element. |
| `defaultValue` | `string` | — | Pre-selected value set by the system. The user can still change it. *(Dropdown only)* |

## Slot Types

Both `leftSlot` and `rightSlot` are independent and accept any element that fits within a **16×16px** area. Neither is required.

| Slot content | Slot | Use case |
|:---|:---|:---|
| **Icon** | Left or Right | Visual cue for the expected data type (search, location, email) |
| **Chevron** | Right | Indicates this input opens a dropdown or selection list |
| **Country flag** | Left | Phone number inputs — shows the selected country and dialing code |
| **Chip** | Left | File upload — shows the selected file name as a compact affordance |
| **Checkbox** | Left (dropdown item) | Multiselect dropdown — each list item carries its own selection state |
| **Clear (✕)** | Right | Allows the user to reset the field value in one tap |

  <strong>Slots are independent.</strong> You can combine any left and right slot freely — a country flag on the left and a clear button on the right, for example. The dropdown list items have their own slot context, separate from the input field's slots.

## Dropdown

A Dropdown extends the Text Input with a chevron in the right slot and an expandable selection list. Use when the user must choose from a predefined set of options.

### Single-select

The input's right slot shows a chevron. Each dropdown item has no slot content — just a label. Only one option can be selected at a time.

<Dropdown
  label="Travel Class"
  options={['Economy', 'Business', 'First Class']}
  placeholder="Select an option"
  hint="Choose the class that applies to this booking."
/>

### Single-select — System default

A value pre-filled by the system — based on a previous selection, a user preference, or a business rule. The user can still open the dropdown and change it.

<Dropdown
  label="Travel Class"
  options={['Economy', 'Business', 'First Class']}
  defaultValue="Business"
  hint="Pre-selected based on your last booking."
/>

### Multi-select

The input field keeps the chevron in its right slot. Each dropdown item's left slot becomes a **checkbox**, enabling independent multi-selection. Selected options are reflected in the input as a count or label summary.

<div style={{background: 'var(--ifm-color-info-contrast-background)', borderLeft: '4px solid var(--ifm-color-info)', borderRadius: '4px', padding: '12px 16px', marginBottom: '24px', fontSize: '14px'}}>
  <strong>Key distinction:</strong> The input field's slots remain unchanged. Only the <em>dropdown list items</em> switch from no-slot to checkbox. This preserves visual consistency of the input while communicating multi-selection at the list level.
</div>

### Disabled

<Dropdown
  label="Region"
  options={['North', 'South', 'East', 'West']}
  placeholder="Automatically assigned"
  state="disabled"
  hint="This field is set by the system."

## When to Use

| Variant | Use when… | Avoid when… |
|:---|:---|:---|
| **Text Input** | The user needs to enter free-form text (name, email, search) | Options are predefined — use a Dropdown instead |
| **Single-select Dropdown** | The user must choose exactly one option from a fixed list | There are more than ~8 options — consider a searchable input |
| **System default** | A value can be inferred from context (last session, user profile, business rule) | No reliable default exists — leave the placeholder instead |
| **Multi-select Dropdown** | The user needs to select multiple options (filters, permissions) | Only one selection makes sense — use single-select |
| **With slot content** | The slot element clarifies the data type or provides a direct action | The slot element is purely decorative — it becomes visual noise |
| **Phone input** | The user needs to enter an international phone number | The product operates in a single country with no dialing code variation |
| **File Upload** | The user needs to attach a file to a form | The upload is a primary page action — use a dedicated upload component |
| **Error state** | Validation fails after the user interacts with the field | The user hasn't interacted yet — don't pre-validate on page load |
| **Disabled state** | The field exists but isn't editable in the current context | The field is permanently irrelevant — remove it from the layout entirely |

## Best Practices

- **Labels:** Keep them short and clear. Never use placeholders as labels.
- **Hints:** Use to provide extra context (e.g., "Password must be 8 characters") or specific, actionable error guidance.
- **Validation:** Trigger the Error state after the user finishes interacting with a field — not on page load.
- **Required fields:** Only mark fields as required if they are strictly necessary. Label optional fields as "(optional)".
- **Disabled vs hidden:** If a field is temporarily unavailable, disable it. If it's permanently irrelevant in the current context, remove it from the layout.
- **Slots:** Each slot should serve one clear purpose — context (left) or action (right). Avoid using both slots decoratively.
- **Dropdown options:** For lists longer than ~8 items, consider adding a search field inside the dropdown or switching to a full search input pattern.
- **System defaults:** Only pre-fill a value when you have reliable context (previous session, user profile, business rule). A wrong default is worse than no default — it creates silent errors.
