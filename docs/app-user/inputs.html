Text input

Inputs allow users to enter and edit text in interfaces. They are essential for forms, search fields, and data entry within the BUSUP ecosystem.

💡 Real Components: The demos below consume our Design Tokens directly from the global CSS. No images — all live HTML.

Component States​

Default​

The resting state before the user interacts. Placeholder text is shown in Neutral 100 (#dbdbdb).

Enter your name as it appears on your ID.

Active (Focus)​

Triggered when the user clicks or tabs into the field. The border changes to Neutral 300 (#989898) and the placeholder becomes typed text in Neutral 400 (#414141).

Enter your name as it appears on your ID.

With Slot Content​

Inputs support independent left and right slots for additional context or actions.

🔍
Try searching by the route number.

Error​

Triggered when validation fails or a required field is submitted empty. Border and hint text switch to Danger 300 (#e53935).

Please enter a valid email address.

Disabled​

Used when a field is locked and cannot be edited. Background becomes Neutral 100 (#dbdbdb), label and hint render in Neutral 200 (#c4c4c4).

This field is automatically generated by the system.

Slot Types​

Both leftSlot and rightSlot are independent and accept any element that fits within a 16×16px area. Neither is required.

Slot contentSlotUse case
IconLeft or RightVisual cue for the expected data type (search, location, email)
ChevronRightIndicates this input opens a dropdown or selection list
Country flagLeftPhone number inputs — shows the selected country and dialing code
ChipLeftFile upload — shows the selected file name as a compact affordance
CheckboxLeft (dropdown item)Multiselect dropdown — each list item carries its own selection state
Clear (✕)RightAllows the user to reset the field value in one tap

Slots are independent. You can combine any left and right slot freely — a country flag on the left and a clear button on the right, for example. The dropdown list items have their own slot context, separate from the input field's slots.

Dropdown​

A Dropdown extends the Text Input with a chevron in the right slot and an expandable selection list. Use when the user must choose from a predefined set of options.

Single-select​

The input's right slot shows a chevron. Each dropdown item has no slot content — just a label. Only one option can be selected at a time.

Single-select — System default​

A value pre-filled by the system — based on a previous selection, a user preference, or a business rule. The user can still open the dropdown and change it.

Multi-select​

The input field keeps the chevron in its right slot. Each dropdown item's left slot becomes a checkbox, enabling independent multi-selection. Selected options are reflected in the input as a count or label summary.

Key distinction: The input field's slots remain unchanged. Only the dropdown list items switch from no-slot to checkbox. This preserves visual consistency of the input while communicating multi-selection at the list level.

Compositions​

These are the established patterns built from the Text Input and its slots. All are in active use across BUSUP products.

Phone Number Input​

The left slot holds a country flag and dialing code. Tapping the flag opens a country selector overlay. The right slot remains available for a clear action.

File Upload​

The left slot becomes a chip showing the "Select a file" affordance before selection, and updates to the filename once a file is chosen. The right slot can hold a remove/clear action.

Pattern in use: This is the standard upload input across BUSUP products. The chip label updates to the filename on selection and can be dismissed via the right slot action.

When to Use​

VariantUse when…Avoid when…
Text InputThe user needs to enter free-form text (name, email, search)Options are predefined — use a Dropdown instead
Single-select DropdownThe user must choose exactly one option from a fixed listThere are more than ~8 options — consider a searchable input
System defaultA value can be inferred from context (last session, user profile, business rule)No reliable default exists — leave the placeholder instead
Multi-select DropdownThe user needs to select multiple options (filters, permissions)Only one selection makes sense — use single-select
With slot contentThe slot element clarifies the data type or provides a direct actionThe slot element is purely decorative — it becomes visual noise
Phone inputThe user needs to enter an international phone numberThe product operates in a single country with no dialing code variation
File UploadThe user needs to attach a file to a formThe upload is a primary page action — use a dedicated upload component
Error stateValidation fails after the user interacts with the fieldThe user hasn't interacted yet — don't pre-validate on page load
Disabled stateThe field exists but isn't editable in the current contextThe field is permanently irrelevant — remove it from the layout entirely

Dos & Don'ts​

Labels & Placeholders​

✅ DO

We'll send your confirmation here.

Use a visible label above the field and a placeholder that shows the expected format. The hint provides extra context below.

❌ DON'T

Don't use the placeholder as a label. Once the user starts typing, the label disappears — leaving them with no context about what the field is for.

Error Feedback​

✅ DO

Please enter a valid email address.

Show specific, actionable error messages in the hint. Tell the user exactly what went wrong and how to fix it.

❌ DON'T

Invalid field.

Avoid generic errors like "Invalid field" or "Error". The user can't fix what they can't understand.

Required Fields​

✅ DO

Mark required fields with * and label optional ones explicitly. This reduces friction and sets clear expectations upfront.

❌ DON'T

Don't mark every field as required. Only ask for information strictly necessary for the process to work.

Slot Usage​

✅ DO

Use each slot with a single, purposeful element. Left slot for context — what the field is for. Right slot for action — what the user can do with the current value.

❌ DON'T

Don't fill both slots with decorative icons. Two icons with no interactive purpose reduce available space for text and create visual noise without adding meaning.

Best Practices​

  • Labels: Keep them short and clear. Never use placeholders as labels.
  • Hints: Use to provide extra context (e.g., "Password must be 8 characters") or specific, actionable error guidance.
  • Validation: Trigger the Error state after the user finishes interacting with a field — not on page load.
  • Required fields: Only mark fields as required if they are strictly necessary. Label optional fields as "(optional)".
  • Disabled vs hidden: If a field is temporarily unavailable, disable it. If it's permanently irrelevant in the current context, remove it from the layout.
  • Slots: Each slot should serve one clear purpose — context (left) or action (right). Avoid using both slots decoratively.
  • Dropdown options: For lists longer than ~8 items, consider adding a search field inside the dropdown or switching to a full search input pattern.
  • System defaults: Only pre-fill a value when you have reliable context (previous session, user profile, business rule). A wrong default is worse than no default — it creates silent errors.
